# Internationalization (i18n)

ChainSettle localizes API error messages and notification-email copy via `src/i18n/`. Locale resolution, adding a new language, and using translations are documented below.

## Locale Resolution Order

1. **Query Parameter:** If `?lang=<locale>` is present in the request query string, it takes precedence (e.g., `?lang=es`).
2. **`Accept-Language` Header:** If no query parameter is provided, the API reads the standard `Accept-Language` header (e.g., `es-MX,es;q=0.9,en;q=0.8`). It resolves to the highest-weighted supported language.
3. **Default:** If neither is present, or if the requested language is unsupported, it falls back to the default locale (`en`).

## Adding a New Locale

To contribute a new language (e.g., French `fr`):

1. **Create the Locale Folder:**
   Create a new folder for your locale under `src/i18n/locales/`:
   ```bash
   mkdir src/i18n/locales/fr
   cp src/i18n/locales/en/common.json src/i18n/locales/fr/common.json
   ```

2. **Translate the Strings:**
   Open `src/i18n/locales/fr/common.json` and translate the string values under the `errors` and `email` objects. 
   *(Note: Leave placeholder variables like `{id}` exactly as they are).*

3. **Register the Locale:**
   Open `src/i18n/i18n.service.ts` and add your new locale code to `SUPPORTED_LOCALES`:
   ```typescript
   export const SUPPORTED_LOCALES = ['en', 'es', 'fr'] as const;
   ```

4. **Verify the Changes End-to-End:**
   Start the application locally and test the fallback and translation behavior:
   ```bash
   # Test via Accept-Language header
   curl -H "Accept-Language: fr" http://localhost:3000/api/v1/...
   
   # Test via query parameter
   curl "http://localhost:3000/api/v1/...?lang=fr"
   ```

## Adding and Using Message Keys

### 1. Add the Key

When you need a new translated string, add it to the `en/common.json` file (and ideally to other supported locales, or let the community translate it later).
```json
{
  "errors": {
    "NEW_ERROR_KEY": "This is a new error regarding {item}."
  }
}
```

### 2. Use it in a Service or Exception

Services can throw standard exceptions using a structured payload with the `i18nKey` and optional `args`:

```typescript
import { NotFoundException } from '@nestjs/common';

// Good: Structured keys allow safe interpolation
throw new NotFoundException({
  i18nKey: 'errors.NEW_ERROR_KEY',
  args: { item: 'shipment' }
});
```

*(Note: The system also supports throwing plain English strings if they exactly match a value in `errors.*` or a regex for a template. The filter reverse-matches and translates, though structured keys are preferred for new code so interpolation stays unambiguous.)*

## Fallback Behavior

- If a specific key is missing from a requested localized file (e.g., `fr/common.json` is missing `errors.NEW_ERROR_KEY`), the i18n service will automatically fall back to the English string from `en/common.json`.
- If the key is missing from the English fallback as well, the raw key (e.g., `errors.NEW_ERROR_KEY`) is returned to the user.
